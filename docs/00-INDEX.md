## Why this order

BRS fixes the claims we may make. SRS turns them into testable requirements. The Threat Model feeds SRS security requirements and the design. PDR and TDD design against all of that. The Evidence Spec and IVM close the loop, so every requirement and every public claim has a named test and a stored evidence file.

## Lock protocol (agile, no big bang)

1. One document per review cycle, with two approved exceptions: the SRS and Threat Model are drafted together, and BRS §15.1a lets *independent* build work start once the SRS is locked. Independent work may proceed; gated work may not.
2. A document moves DRAFT, then REVIEW (you comment), then LOCKED vX.0 only after you write "approve" for that document.
3. LOCKED means changes need a change request: ID, what changes, why, and which downstream documents are affected.
4. Items marked **GATED-BY-SPIKE** are locked only as questions. They get answered by a short spike with a result file, then the document gets a minor revision (v1.1).
5. Frontend and UI are not specified in these documents beyond an API contract and constraints. Your UI agent gets a separate prompt (written after the TDD is locked).
